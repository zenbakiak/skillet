# 0017. Resource limits for JavaScript plugins (QuickJS)

- Status: Accepted (2026-11-21: limits option B, §6 option H1, `httpGet` is removed)
- Date: 2026-11-20
- Deciders: Maintainer (accepts), Security Reviewer (author), Rust Engineer
- Related: BL-018, ADR-0007 (extensibility), ADR-0011 (evaluation budget and deadline),
  ADR-0008 (thread-pool servers), `src/js_plugin.rs`, `src/limits.rs`,
  [threat model](../security/THREAT_MODEL.md) §2.5

## Context
`JavaScriptFunction::execute` (`src/js_plugin.rs`) creates a fresh `rquickjs` 0.11 `Runtime` and
`Context::full` per call, defines a global `httpGet`, evaluates the hook source and calls
`execute(args)`. It sets no limits. ADR-0011 bounds what the Skillet evaluator does, but explicitly
leaves memory and CPU *inside* QuickJS to this decision, and asks that the interrupt handler use
the same deadline (`limits::deadline_passed()`, already in `src/limits.rs`, crate-private).

Who can run JS: the admin (upload endpoints) and whoever writes files into the hooks directory.
Who can *trigger* JS: every eval client, with arguments it chooses. So a hook whose work depends on
its input (a loop over `args[0]`, a string built from it) is reachable by untrusted users, and an
admin mistake in a hook is a server-wide outage.

### What rquickjs 0.11 offers (checked in `rquickjs-core-0.11.0/src/runtime/base.rs`)

| API | Behaviour |
|---|---|
| `Runtime::set_memory_limit(usize)` | Hard cap on the runtime's malloc total; `0` = unlimited. **No-op with a custom allocator** (`rust-alloc` / `allocator` features). We use default features, so it works. |
| `Runtime::set_max_stack_size(usize)` | JS stack limit, default 256 KiB, measured from the stack top at runtime creation. |
| `Runtime::set_interrupt_handler(Option<Box<dyn FnMut() -> bool>>)` | Called regularly while bytecode runs; `true` raises an **uncatchable** "interrupted" exception. The closure is `'static` and runs on the calling thread, so it may read thread-locals such as the ADR-0011 budget. |
| `Runtime::memory_usage()` | `malloc_size` and friends, for reporting. |
| `Ctx::catch()` | Returns the pending exception, with its message and stack. |

### Measurements (2026-11-20, macOS arm64, release builds, 127.0.0.1 only)
Server: release `sk_http_server --threads 2|4 --token … --admin-token …`, `SKILLET_HOOKS_DIR`
pointing at a temp directory with one test hook per case. Limit prototypes: a scratch crate
outside the repo depending on `rquickjs = "=0.11.0"` (same version, same features).

**Today (no limits), through the HTTP server:**

| Case | Result |
|---|---|
| Hook `while (true) {}` | Client gave up after 15 s with no response; the worker kept spinning (85% CPU, then 177% with two). The 10 s evaluation deadline never fires inside JS. |
| Two such requests, 2 workers | Server stopped answering: `=2+3` and `GET /health` both timed out. Only a restart helps. |
| `@example` that loops, on `POST /upload-js` | The upload never answers (validation runs the example); the worker is pinned and the file is not written. |
| Hook allocates `"x".repeat(4e8)` | Succeeded in 3.8 s; server RSS 11 MB → 402 MB, and it stayed there. Nothing counted it. |
| Hook recursion `f(n) { return f(n+1)+1 }` | Error after 1 ms (QuickJS's default 256 KiB stack). Text: `JS function execution failed: Exception generated by QuickJS` (the real `RangeError` message is lost). |
| Hook returns a nested array, depth 200 | `Expression nested too deeply (max 128)`, as expected. |
| Hook returns depth 200,000, or a cyclic array (`a.push(a)`) | **Process abort**: `thread '<unknown>' has overflowed its stack`, server gone. Same with `sk` (exit 134). `js_to_value` recurses before any depth check. |
| Hook calls `httpGet` on a peer that accepts and never answers | Worker held for all 15 s we waited; the `curl` child was still running. |
| Hook loops, then `POST /reload-hooks`, then a new `=ABS(-7)` (4 workers) | Reload and `ABS` both hang: the hook holds the registry read lock, the waiting writer blocks new readers. Cached results still answer. |

**With limits (prototype, one runtime per case):**

| Case | Limit | Result |
|---|---|---|
| `while(true){}` | interrupt at 100 ms deadline | stopped at 100.2 ms, `interrupted` |
| `while(true){}` | interrupt at 1 s | stopped at 1005.8 ms |
| `for(;;){ try { while(true){} } catch(e){} }` | interrupt at 100 ms | stopped at 100.3 ms (not catchable) |
| `'x'.repeat(4e8)` | memory 64 MiB | `out of memory` after 0.5 ms; process max RSS 68 MB for the whole run |
| `for(;;) a.push({...})` | memory 64 MiB | stopped at the limit (malloc 65,535 KB) after 648 ms |
| runaway recursion | stack 256 KiB (default) or 1 MiB | `Maximum call stack size exceeded`, < 0.3 ms |
| Rust host function sleeps 1.5 s, deadline 100 ms | interrupt | stopped only after **1504 ms**: the interrupt cannot fire inside a host call |
| 20M-iteration JS loop, best of 5 | with vs. without handler | 1155 ms vs. 1484 ms (no measurable overhead; difference is noise) |
| Create runtime + context, eval `1` | with vs. without limits | 86 µs vs. 84 µs |

## Decision (accepted: §1–§5 as written, option B; §6 option H1)

### 1. Memory: `JS_MEMORY_LIMIT = 64 MiB` per call
Call `set_memory_limit(64 MiB)` on every runtime. Hooks are small pure functions: a runtime
that has evaluated a small script holds about 95 KB (measured, `malloc_size`), and the shipped
`mx_isr.js` is a 3.6 KB table lookup. 64 MiB leaves more than two orders of magnitude of headroom and keeps the
server worst case at `threads × (512 MB evaluation + 64 MB JS)`. Arguments converted into JS count
against the limit, so a hook that receives a very large string (tens of MB) fails cleanly instead of
doubling memory. Never enable rquickjs's `rust-alloc`/`allocator` features: they turn the limit
into a no-op (add a comment next to the dependency in `Cargo.toml`).

### 2. Stack: `JS_MAX_STACK = 256 KiB`, set explicitly
This equals the rquickjs default, which already caught runaway recursion. Setting it explicitly
makes it a reviewed constant and documents that it must stay well below the smallest thread that
runs JS (16 MB server workers, 8 MB main thread, 2 MB default `std::thread` for embedders).

### 3. Time: interrupt on the ADR-0011 deadline **or** a per-call cap
The interrupt handler returns `true` when `limits::deadline_passed()` **or** when
`JS_CALL_TIMEOUT = 10 s` has passed since the call started. The handler only reads the clock;
QuickJS calls it often enough (100 ms deadline → stopped at 100.2 ms) at no measurable cost.
- In the servers the request deadline usually fires first, so one 10 s limit covers the whole
  request, JS included. When it does, the JS call reports the ADR-0011 timeout (the Rust engineer
  adds a crate-private `limits` helper to record the timeout trip, so the evaluation returns
  `Evaluation timed out (max 10 s)` even if a formula swallows the JS error).
- Outside an evaluation deadline (`sk`, the library, upload validation, `/reload-hooks`) the
  per-call cap is the only bound. That is why the cap is needed: an infinite loop is never a
  valid result, and JS hooks are not deterministic anyway (see §6), so ADR-0011's "no deadline in
  the library" rule, which protects deterministic results, does not apply to them.

### 4. Converting results back: bounded depth, cycles rejected
`js_to_value` (and `value_to_js`) take a depth parameter and fail at `MAX_NESTING_DEPTH` (128)
with the existing `Expression nested too deeply (max 128)` error. A cyclic array hits the bound,
so no separate cycle check is needed. Objects already go through `JSON.stringify`, which throws on
cycles; its result is a `Json` string, charged and depth-checked as today.

### 5. Error texts
Use the real QuickJS exception (`ctx.catch()`), not the generic "Exception generated by QuickJS".
`NAME` is the hook's `@name`.

| Cause | Error text |
|---|---|
| Request deadline passed (servers) | `Evaluation timed out (max 10 s)` (ADR-0011 text, unchanged) |
| Per-call cap | `JS function NAME timed out (max 10 s)` |
| Memory limit | `JS function NAME ran out of memory (max 64 MB)` |
| Stack limit | `JS function NAME failed: RangeError: Maximum call stack size exceeded` |
| Any other exception | `JS function NAME failed: <exception message>` |
| Result too deep or cyclic | `Expression nested too deeply (max 128)` |

All are ordinary evaluation errors (HTTP 400, `success: false`), like every other limit.

### 6. Network access from hooks (`httpGet`): maintainer decision required
Every runtime defines `httpGet(url)`, which runs the `curl` binary with the JS string as its only
argument. It is undocumented and no hook in the repository uses it. Verified on 127.0.0.1:
- `file://` URLs return any file the server user can read;
- loopback and internal addresses are reachable (a hook fetched the server's own `/health`);
- an argument starting with `-` is parsed by curl as an option (`--version` returned curl's
  version banner);
- no timeout: the interrupt handler cannot stop a blocked host call (prototype: a 1.5 s host call
  overran a 100 ms deadline to 1504 ms), so a slow peer holds the worker indefinitely.

This contradicts the threat model's "no host FS/net access" for plugins and AGENTS.md's "no I/O
from expressions". Options:

- **H1 (recommended): remove `httpGet`.** Hooks become pure functions of their arguments. Smallest
  attack surface; removes the `curl` runtime dependency. Breaking only for deployments that found
  and used the undocumented global; record it in the changelog.
- **H2: keep it, opt-in and hardened.** Off by default; enabled by an operator setting (for example
  `SKILLET_JS_HTTP=1`, or a `js-http` cargo feature). When on: pass `--proto =http,https
  --proto-redir =http,https --max-time <min(remaining deadline, 5 s)> --max-filesize 1M --`
  before the URL, or replace curl with an in-process client with the same limits; optionally a
  host allowlist. SSRF to whatever the allowlist permits remains, and must be documented.
- **H3: keep as is.** Rejected: unauthenticated file read on the default Docker image (threat model
  §2.8).

### 7. Out of scope here, filed separately
- Release the registry lock before running a custom function (store `Arc<dyn CustomFunction>`,
  clone it out, drop the guard). With §3 the stall is bounded at 10 s, but it still blocks every
  uncached evaluation that calls a function while a reload waits.
- Path traversal in the upload/update/delete endpoints; development mode with JS management
  enabled; `Access-Control-Allow-Origin: *`; the Docker defaults (threat model §2.3, §2.5, §2.8).

## Options considered for limits (§1–§3)

| Option | Memory | Stack | Time | Verdict |
|---|---|---|---|---|
| A | 64 MiB | 256 KiB | `deadline_passed()` only | Servers safe during `/eval`; `sk`, library, upload validation and reload still unbounded in time |
| **B (recommended)** | 64 MiB | 256 KiB | `deadline_passed()` **or** 10 s per call | Bounds every path; one constant to explain |
| C | as B, plus `EvalLimits` fields `js_memory` / `js_timeout` | | | Additive later (`EvalLimits` is `#[non_exhaustive]`); defer until an embedder asks |
| D | memory tied to the remaining evaluation budget (`min(64 MiB, remaining)`) and QuickJS `malloc_size` charged after the call | | | More precise, but couples two different units (real bytes vs. the ADR-0011 cost model) and makes JS failures depend on what ran before; not now |
| E | Run JS on a separate thread or process and kill it on timeout | | | Rejected: Rust threads cannot be killed; a process per call costs far more than the 85 µs runtime setup |

Memory alternatives: 32 MiB (tighter, risks hooks with lookup tables), 256 MiB (same number as the
budget, but then the server worst case per thread doubles). Time alternatives: 1 s or 5 s per call
(safer for the CLI, but a second number next to the 10 s deadline).

## Consequences
- \+ No hook can pin a worker for longer than 10 s, allocate more than 64 MiB, or abort the
  process through its result. The overhead is not measurable (86 µs vs. 84 µs per call setup).
- \+ JS errors become readable.
- − Behaviour change: hooks that ran longer than 10 s, used more than 64 MiB, or returned arrays
  deeper than 128 now fail. None of the shipped hooks or tests come close.
- − Host functions (today only `httpGet`) are outside the interrupt; each must bound its own time.
  Under H1 there are none.
- − Under H1, deployments using `httpGet` break (it was never documented).
- Tests to add (QA): a hook that loops (fails within ~10 s on a server, and on `sk` with the per-call
  cap; a short cap via a test-only override keeps the test fast), allocates 400 MB, recurses,
  returns a cyclic array and a depth-200,000 array (error, process alive), and a loop inside
  `try/catch` (still interrupted).
